# MKnote 整体体验与架构优化计划

> 日期：2026-07-07
> 目标：在不推倒重写、不改变用户数据格式的前提下，系统性改善 MKnote 的顺滑度、代码结构、扩展性和界面动效。
> 原则：先观测，再拆分；先低风险，再高收益；每阶段可单独验收、可暂停、可回滚。

---

## 0. 当前判断

MKnote 当前已经具备较完整的产品功能，但代码进入了功能堆叠后的臃肿期。主要表现为：

- `src/App.tsx` 承担过多职责：编辑状态、保存流程、Tab、资料库、窗口事件、配置、思源、消息中心等都集中在主组件。
- `src/components/CompactView.tsx` 既包含主界面布局，也包含大量设置面板、弹窗、工具栏和业务交互。
- 前端直接散落调用 Tauri `invoke`、window API 和 event API，UI 层与桌面壳强耦合。
- 保存、列表刷新、索引刷新和 Tab 持久化之间有连锁关系，可能影响输入和切换手感。
- 动效系统尚未成体系，很多状态切换是“突然出现/消失”，降低了软件的精致感。

这不是必须换技术栈的问题。优先路线应是：在现有 Tauri + React 架构上做分阶段收敛和体验优化；只有优化后仍确认窗口壳层是瓶颈，再考虑 WPF + WebView2 验证。

---

## 1. 总体落地顺序

1. 加轻量性能标记，确认输入、切换、后端调用耗时。
2. 做 `appBridge`，隔离 Tauri 调用，建立后续优化和迁移边界。
3. 优化保存队列和索引刷新时机，让输入链路变轻。
4. 把 `App.tsx` 的高频状态拆出去，先保证输入不牵动全局。
5. 继续拆分资料库、Tab、窗口事件、设置面板等中低频模块，降低整体臃肿度。
6. 建 motion tokens，补资料库、Tab、弹窗、状态栏、视图切换动画。
7. 最后评估是否需要 WPF 壳验证。

说明：用户原始顺序中 `appBridge` 在保存优化之后。实际实施建议将 `appBridge` 提前到第 2 步，因为它是低风险边界层，也能统一后端调用计时；但不改变整体目标。

## 2. 阶段一：性能标记与诊断

### 目标

不改业务行为，只建立可观测性，回答三个问题：

- 输入时到底是编辑器卡、React 重渲染多，还是保存链路慢？
- 切换笔记时慢在 `read_note`、`list_notes`、Tab 状态，还是 UI 渲染？
- 后端 `invoke` 哪些命令耗时高、调用频率高？

### 实施内容

- 新增轻量性能工具，例如 `src/utils/perf.ts`。
- 支持开发环境下输出计时，生产环境默认静默。
- 标记关键路径：
  - 应用初始化：`get_app_state`、`refreshAll`、恢复 tabs。
  - 输入链路：`onContentChange`、字数/行数计算、历史入栈、防抖保存触发。
  - 保存链路：排队、实际 `write_note`、保存完成、失败。
  - 笔记切换：flush 当前笔记、读取目标笔记、更新 active session。
  - 后端调用：统一统计 command 名称、耗时、失败。

### 不做的事

- 不改保存策略。
- 不拆组件。
- 不加动效。
- 不修改用户数据格式。

### 验收标准

- `npm run build` 通过。
- 开发模式下可看到关键路径耗时日志。
- 日志不会刷屏到影响使用，支持开关。
- 普通用户构建不出现调试噪音。

### 风险

低。主要风险是日志过多或计时包装影响类型推断。

## 3. 阶段二：`appBridge` 隔离 Tauri 调用

### 目标

将散落在 UI 组件里的 Tauri 直接调用收敛到统一边界层，提升代码优雅度和可测试性，并为未来 WPF + WebView2 PoC 留出替换口。

### 建议结构

```text
src/
  services/
    appBridge.ts          # 通用 invoke / event / window wrapper
    notesService.ts       # 笔记 CRUD
    configService.ts      # 配置项读写
    libraryService.ts     # 资料库/文件夹/颜色
    windowService.ts      # show/hide/drag/always-on-top
    messageHubService.ts  # 短消息和保险库
    siyuanService.ts      # 思源
```

第一步不必一次性拆所有 service，可以先建立：

- `appBridge.invoke<T>(command, args, options?)`
- `appBridge.listen<T>(event, handler)`
- `appBridge.window.show/hide/startDragging/setAlwaysOnTop`
- `appBridge.dialog.open`

### 实施内容

- 新增 `src/services/appBridge.ts`。
- 在桥接层内接入阶段一的性能计时。
- 先替换高频和核心路径：
  - `read_note`
  - `write_note`
  - `list_notes`
  - `set_open_tabs`
  - `refresh_agent_index`
  - `show_window` / `hide_window`
- 后续逐步替换其余 `invoke`。

### 不做的事

- 不改变 Rust command 名称。
- 不改变返回类型。
- 不改业务逻辑。
- 不引入新状态管理库。

### 验收标准

- `npm run build` 通过。
- 搜索 `@tauri-apps/api/core`，应逐步减少到只在 `appBridge.ts` 出现。
- 关键 `invoke` 日志能显示 command 名称和耗时。
- 新建、读取、保存、切换、隐藏窗口功能无行为变化。

### 风险

低到中。主要风险是 Tauri window/event API 的调用上下文差异，需分批替换。

## 4. 阶段三：保存队列与索引刷新优化

### 目标

让输入路径保持轻量，避免保存、索引、列表刷新、Tab 持久化互相牵连。

### 当前可疑点

- 输入后更新 `content`、`dirty`、`saveStatus`，可能带动主组件大范围重渲染。
- 保存完成后可能触发过多刷新。
- `refresh_agent_index` 应只在结构性变化后触发，而不是跟随高频内容保存。
- 多 Tab / 弹出窗口 / 胶囊窗口的保存路径需要统一规则。

### 实施内容

- 新增或整理 `useSaveQueue`：
  - 同一笔记多次输入，只保留最后一次待保存内容。
  - 保存串行化，避免同一文件并发写。
  - 组件卸载、切换笔记、隐藏窗口前强制 flush。
  - 保存失败保持错误状态，不吞错。
- 明确索引刷新策略：
  - 内容保存：默认不立即 `refresh_agent_index`。
  - 创建、删除、重命名、移动、恢复、清空回收站：触发索引刷新。
  - 可选：应用空闲时批量刷新索引。
- 列表更新策略：
  - 当前笔记内容保存后，只更新当前项 modified time 或局部状态。
  - 不做全量 `list_notes`，除非结构变化。

### 不做的事

- 不改变 `.md` 存储格式。
- 不改变回收站格式。
- 不改变 Agent manifest 结构。

### 验收标准

- 连续打字无明显保存卡顿。
- 切换笔记前能可靠保存。
- 退出/隐藏窗口前能可靠保存。
- 新建/删除/重命名/移动后 manifest 仍能刷新。
- `refresh_agent_index` 调用次数显著减少。

### 重点回归

- 普通笔记自动保存。
- 待办事项保存。
- Popout 窗口保存。
- Capsule 保存/关闭。
- 切换 Tab 前保存。
- 隐藏到托盘前保存。

### 风险

中。保存链路是核心路径，必须小步推进，先加测试/日志，再替换实现。

## 5. 阶段四：拆分 `App.tsx` 高频状态

### 目标

减少输入时主应用全局重渲染，把高频状态隔离到小范围组件或 hook 中。

### 建议拆分

```text
src/hooks/
  useNoteSession.ts       # active note、content、dirty、saveStatus、flushSave
  useNoteTabs.ts          # openTabs、pinnedTabs、tab 持久化、关闭/置顶
  useLibraryState.ts      # folders、notes、colors、refreshAll、筛选
  useWindowEvents.ts      # Tauri event/listen，show/hide/focus revision
  useRecentNotes.ts       # 最近打开
  useSiyuanSyncState.ts   # 思源状态
```

优先拆高频：

1. `useNoteSession`
2. `useNoteTabs`
3. `useLibraryState`

### 实施策略

- 先抽 hook，不改 UI 树。
- 保持原 props 名称和行为。
- 每抽一个 hook，单独 build 和手动验收。
- 对编辑器相关组件做 `memo`，让内容输入只影响编辑器和状态栏必要字段。

### 不做的事

- 不引入 Redux/Zustand 等新库，除非后续证明必要。
- 不做大规模命名重构。
- 不同时重写 UI。

### 验收标准

- `App.tsx` 行数和职责明显下降。
- 打字时资料库、设置、消息中心、Tab 非必要部分不频繁重渲染。
- 核心功能无行为变化。

### 风险

中到高。`App.tsx` 是总控文件，拆分时最容易漏依赖或闭包状态过期。需要借助阶段一的性能日志和严格手动验收。

  EditorToolbar.tsx

### 不做的事

### 风险

中。主要风险是 props 透传遗漏和弹窗状态归属混乱。

## 7. 阶段六：motion tokens 与动效补全

### 目标

建立统一动效语言，让软件从“功能可用”变成“使用顺手、反馈自然”。

### Motion Token 建议

放入 `src/styles/tokens.css`：

```css
:root {
  --mk-motion-fast: 100ms;
  --mk-motion-base: 160ms;
  --mk-motion-panel: 220ms;
  --mk-motion-ease-out: cubic-bezier(0.16, 1, 0.3, 1);
  --mk-motion-ease-standard: cubic-bezier(0.2, 0, 0, 1);
  --mk-motion-scale-press: 0.97;
}
```

同时加 `prefers-reduced-motion`：

```css
@media (prefers-reduced-motion: reduce) {
  * {
    animation-duration: 1ms !important;
    transition-duration: 1ms !important;
  }
}
```

### 动效范围

- 资料库面板：滑入/淡入，关闭时淡出。
- 设置面板：弹层 scale 0.98 → 1 + opacity。
- Tab：
  - active 状态色条移动。
  - 新增/关闭轻微 fade/slide。
  - 置顶状态 icon 颜色过渡。
- 状态栏：
  - 保存中/已保存/错误状态淡入淡出。
  - 操作按钮 hover/press 统一反馈。
- 搜索/Omnibox：
  - 打开时轻微下落 + fade。
  - 结果列表 stagger 不超过 40ms。
- 视图切换：
  - 编辑/预览切换轻微 fade。
  - 消息中心/资料库/默认编辑区切换避免闪烁。
- 拖拽导入：
  - overlay 缓入缓出。

### 动效原则

- 不使用重动画。
- 不让动画阻塞输入。
- 所有动画只使用 `opacity`、`transform`，尽量避免频繁触发布局。
- 不给长文本容器做复杂动画，避免滚动和输入卡顿。

### 验收标准

- 动效统一、轻快、不会遮挡操作。
- 输入和滚动不因动画变卡。
- 支持系统减少动画设置。
- 浅色/深色/多主题下表现一致。

### 风险

中。动画容易引发布局抖动和“看起来像 bug”的错觉，必须放在逻辑稳定后实施。

## 8. 阶段七：WPF 壳验证判断

### 触发条件

只有满足以下情况才进入 WPF PoC：

- 阶段一到六完成后，输入、切换、保存、动效已优化。
- 仍然存在明显窗口级不顺滑：
  - 显示/隐藏窗口不干脆。
  - 置顶/焦点/托盘行为异常。
  - 拖动窗口或多窗口体验明显不如原生。
- 性能日志显示问题主要不在 React 渲染或后端调用，而在壳层窗口行为。

### PoC 范围

仅验证 `WPF + WebView2 + appBridge adapter`：

- 加载现有 React build。
- 实现最小 command bridge：
  - `get_app_state`
  - `read_note`
  - `write_note`
  - `list_notes`
  - `show_window`
  - `hide_window`
- 验证窗口显示/隐藏、置顶、托盘、热键。

### 不做的事

- 不原生重写 WPF UI。
- 不迁移全部后端功能。
- 不替换主线应用。

### 验收标准

- 能客观比较窗口级手感。
- 能判断是否值得继续投入 WPF 路线。

## 10. 风险控制与回滚策略

- 每阶段单独提交或至少保持清晰 diff。
- 不混合“结构拆分”和“视觉动效”。
- 不改用户数据格式。
- 不改 Rust command 名称和参数，除非单独立项。
- 对保存、删除、移动、回收站等数据操作保持最小改动。
- 如果某阶段出现难以定位的问题，先回退该阶段，不继续叠加后续优化。
